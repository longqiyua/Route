#### 1. 核心格式

所有版本号严格遵循以下格式： `V{主版本}.{次版本} {阶段后缀}`

- **示例**：`V1.0`, `V1.1 update.`, `V0.9 Lab`, `V2.0 pre.`
- **注意**：`V` 必须大写，数字之间用 `.` 分隔，后缀与版本号之间保留一个空格。

#### 2. 版本号定义规则

| 组成部分      | 格式         | 触发条件                       | 说明                                                                   |
| --------- | ---------- | -------------------------- | -------------------------------------------------------------------- |
| **主版本**   | `V{X}.0`   | **架构重构 / 重大功能迭代 / 首次正式发布** | 代表产品的里程碑式更新。只有当核心逻辑、UI 框架或底层算法发生根本性变化时，才提升主版本号。                      |
| **次版本**   | `V{X}.{Y}` | **核心功能新增 / 模块级优化**         | 代表在现有架构下的实质性功能扩充。例如：GOTO Engine 新增了 T9 纠错算法，或 GOTO Base 引入了新的向量索引策略。 |
| **修订/补丁** | `update.`  | **Bug 修复 / 细微功能补充 / 性能微调** | 不改变核心功能逻辑，仅用于维持系统稳定或小幅体验优化。后缀固定为 `update.`。                          |

#### 3. 阶段后缀定义 (Stage Suffixes)

后缀用于标识版本的**稳定性**和**发布状态**，必须严格对应以下场景：

- **`Lab` (实验室版本)**
  - **格式示例**：`V0.9 Lab`
  - **定义**：极高不确定性版本。用于验证全新的技术路线或实验性功能。
  - **特征**：可能存在严重崩溃、数据丢失风险，仅限开发者内部调试使用。
  - **约束**：主版本号通常为 `0`，表示产品尚未成熟。
- **`beta` (测试版本)**
  - **格式示例**：`V0.X beta`
  - **定义**：功能基本完整，但存在已知 Bug 或不稳定因素。
  - **特征**：面向小范围核心用户或测试组开放，用于收集反馈和压力测试。
- **`pre.` (预览版本)**
  - **格式示例**：`V1.0 pre.`
  - **定义**：即将发布的正式版的候选版本。
  - **特征**：功能已冻结，主要进行最后的兼容性测试和 UI 细节打磨。稳定性较高，接近正式版。
- **`update.` (更新/补丁版本)**
  - **格式示例**：`V1.0 update.`
  - **定义**：基于正式版的微小迭代。
  - **特征**：修复紧急 Bug 或增加极小的辅助功能。不涉及核心逻辑变更。
- **(无后缀)**
  - **格式示例**：`V1.0`, `V2.1`
  - **定义**：正式稳定版 (Stable Release)。
  - **特征**：经过充分测试，面向所有用户推送的稳定版本。

#### 4. 演进逻辑示例

1. **起步阶段**：
   - `V0.1 Lab` -> `V0.5 beta` -> `V0.9 Lab` (尝试新算法) -> `V0.9 beta`
2. **首次正式发布**：
   - `V1.0` (里程碑，核心功能闭环)
3. **日常维护**：
   - `V1.0 update.` (修复了一个闪退 Bug)
   - `V1.0 update.` (优化了启动速度)
4. **核心功能迭代**：
   - `V1.1` (新增了 GOTO Where 智能通知模块)
   - `V1.1 update.` (修复通知延迟问题)
5. **下一代架构**：
   - `V2.0 pre.` (重构了 GOTO Base 的 RAG 索引库)
   - `V2.0` (全新架构正式发布)
